## 1. 목적

가상 로봇(과 물건, 컨베이어 같은 오브젝트)을 **Python 스크립트로 제어하고**, 기구학/동역학/제어 계산은 **사용자가 갈아 끼울 수 있는 DLL**이 맡게 한다. 3D 화면(Simul_View)과 엔진은 계산 결과를 그리고, 시간 적분과 충돌 같은 물리의 기반을 담당한다.

## 2. 구성도 [결정: 사용자 스케치 기준]

```
┌─ system ───────────────────────────────────────────────────────┐
│  [Simul_View + Object] ◀──양방향──▶ [Python] ◀── [DLL] ◀── [DLL Maker]  │
└────────────────────────────────────────────────────────────────┘
```

- **Simul_View / Object**: 3D 화면과 오브젝트(모델, 물건, 로봇). 이미 구현된 엔진(C++11, Ubuntu 20.04 + Windows MSVC)이다.
- **Python**: 오브젝트와 양방향으로 주고받는 허브. **명령 전달기 수준**으로 둔다.
- **DLL**: 기구학, 동역학, 정역학, 제어 계산. 사용자가 직접 만들어 갈아 끼운다.
- **DLL Maker**: 우리 시스템에 맞는 DLL을 쉽게 만들도록 돕는 도구 [열림: 범위 미정, 3.4 참고].

## 3. 역할 분담

### 3.1 엔진이 쥐는 것 [제안]
시간 적분(틱, dt), 상태 저장, 충돌, 바닥/낙하, 그리기. 적분까지 사용자 DLL에 맡기면 사용자마다 결과와 안정성이 달라지고 화면과 상태가 어긋날 수 있다. DLL은 "계산 결과"를 돌려주고 엔진이 적분한다.

### 3.2 DLL이 맡는 것 [결정]
모터 제어를 위한 기구학, 동역학, 정역학 처리. 사용자가 직접 처리할 수 있게 한다.

갈아 끼우는 지점 (우선순위) [제안]:
1. **제어기**: (현재 상태, 목표) → 모터 명령(토크 또는 속도). 가장 작고 가장 많이 바꾸는 부분. 중력 보상(정역학), PID 등. 실제 로봇의 모터 드라이버 경계와 같게 잡으면 나중에 실제 로봇에 이식할 수 있다.
2. **동역학 모델**: (q, qd, 토크) → qdd. 기본값은 현재 RNEA 기반 계산. 마찰, 탄성, 모터 모델을 바꾸고 싶을 때. 1번이 안정된 뒤에 추가.
3. **기구학(FK/IK)**: 보통 URDF로 정해지므로 선택 지점.

### 3.3 Python이 맡는 것 [결정]
오브젝트 사이의 로직과 명령 전달. 계산은 하지 않는다. 시간과 상태를 DLL에 전달하는 구조도 허용한다 (제어 주기가 낮아 가능, 4절 참고).

### 3.4 DLL Maker [열림]
"우리 시스템에 맞는 DLL을 만드는 데 도움을 주는 도구"까지만 정해졌다. 후보 (작은 것부터):
1. 틀(SDK) 제공: 규격 헤더 + 예제 DLL + 빌드 스크립트 **(처음에는 이것을 권장)**
2. 명령으로 생성: `dll_maker new/build`
3. 명세 파일에서 코드 생성: 규격이 굳은 뒤에

## 4. 호출 경로와 시간 [결정/제안]

- 제어 주기: 로봇 쪽에서 1 kHz까지 가는 일이 없다 → Python 경유가 현실적. 제어 주기는 설정값으로 둔다 (시뮬레이션 틱과 같게, 또는 정수 배로 낮춤).
- **lockstep** [제안]: 한 틱마다 상태를 Python에 넘기고, DLL 결과(토크 등)를 받은 뒤 그 틱을 적분한다. Python이 느려도 결과는 항상 같다 (결정성).
- DLL 규격은 호출하는 쪽을 가리지 않게 고정 [제안]: 지금은 Python이 부르고, 나중에 부르는 쪽만 C++로 바꿔도 DLL은 그대로.

```c
// 제어기 DLL 규격 (초안, C ABI)
void* ctrl_create(const char* configJson);
void  ctrl_destroy(void* h);
int   ctrl_update(void* h, double t, double dt,
                  const double* q, const double* qd, int n,     // 현재 상태
                  const double* target, int nt,                  // Python 이 보낸 목표
                  double* out, int nout);                        // 모터 명령
```
단위는 엔진 규칙(m, rad, 쿼터니언).

## 5. Object 클래스 (Python SDK) [결정: 방향 / 제안: 세부]

- 스크립트는 **오브젝트마다** 붙인다 [결정].
- Python에 `Object` 기본 클래스를 미리 설계하고, 사용자는 **서브클래싱**해서 쓴다 [결정].

```python
class Object:
    name: str                       # 엔진의 오브젝트 이름(경로)
    # 엔진이 채워 줌
    handle                          # (슬롯, 세대)
    q, pose                         # 읽기 전용 뷰
    def command(self, name, *args)  # 쓰기는 항상 명령 큐로
    def send(self, other, event, **data)   # 오브젝트 간 메시지
    # 사용자가 오버라이드
    def on_start(self): ...
    def on_tick(self, t, dt): ...
    def on_event(self, event): ...
    def on_stop(self): ...
```

규칙 [제안]:
- 상태 속성은 틱 사이에서만 바뀐다. `command()`는 다음 틱 시작에 처리된다.
- 오브젝트끼리 직접 부르지 않고 엔진의 메시지(이벤트)를 거친다.
- 스크립트 호출 순서는 고정(생성 순서). 예외는 그 오브젝트만 멈추고 로그에 남긴다.
- 모든 스크립트가 같은 **시뮬레이션 시간**을 쓴다 (`sleep` 대신 `wait`).
- API 버전을 두어 맞지 않으면 시작 때 거부한다.
- 첫 공개 API는 작게: `on_start/on_tick/on_event/on_stop`, `command`, `send`, 읽기 속성 몇 개.

클래스와 오브젝트 연결 방식 [열림]: (1) `arm.urdf` 옆 `arm.py`에서 자동 탐색, (2) `@bind("robot1")` 데코레이터, (3) 장면 설정 파일. 1을 기본, 2를 보조로 제안.

## 6. 데이터 교환: 공유메모리 + 해시 검색 [사용자 의견: 선호 / 우려 있음]

### 6.1 사용자가 제안한 방향
- 이름 기반으로 오브젝트를 찾고, 공유메모리로 데이터를 주고받는다.
- 오브젝트는 해시 트리(해시 테이블) 같은 구조에 넣어 빠르게 검색한다.

### 6.2 설계 초안 [제안]
```
[헤더]  매직, 레이아웃 버전, 전체 크기, 틱 번호, 레지스트리 버전, 오브젝트 수
[해시 테이블]  이름 해시 → 슬롯 번호 (오픈 어드레싱, 고정 크기)
[슬롯 배열]  이름, 세대 번호, 부모/첫 자식/다음 형제 슬롯, 데이터 위치
[데이터 영역]  오브젝트별 상태 블록 (q, qd, 위치/자세, 플래그)
[명령 링 버퍼]  Python → 엔진
```
- 이름은 계층 경로(`robot1/arm/joint1`)의 전체 문자열이 해시 키. 64비트 FNV-1a 등 단순한 해시, 충돌은 저장한 이름과 비교해 걸러낸다.
- 포인터 대신 오프셋/슬롯 번호만 쓴다. 핸들은 `(슬롯, 세대)`라 지워진 오브젝트의 옛 핸들은 안전하게 거부된다.
- 검색은 이름을 핸들로 바꿀 때만. 틱 경로에서는 핸들로 바로 읽는다.
- 동기화: 쓰기는 엔진 하나, 읽기는 Python. 상태 블록은 시퀀스 번호(seqlock), lockstep은 헤더의 틱 번호.
- 고정 크기(최대 오브젝트 수, 이름 길이, q 개수)를 처음에 정한다. 플랫폼 래퍼는 Windows `CreateFileMapping`, Ubuntu `shm_open`.
- 구현은 "메모리 덩어리 위에서 동작"하는 형태로 만들어 일반 메모리에서 먼저 테스트하고 같은 코드를 공유메모리에 올린다. `CBase` std-free 규칙을 따른다.

### 6.3 우려 (사용자 지적) 와 Claude 의견
사용자 우려: "시뮬레이션으로 사용하기에는 이 방법이 좋지 않을 것 같다".
- 공유메모리 해시 구조를 **시뮬레이션 계산의 저장소**로 쓰면 좋지 않다. 동역학/충돌은 연속 배열이 유리하고, 동기화 비용과 고정 크기가 맞지 않는다.
- **외부와 주고받는 창구**로만 쓰면 괜찮다. 엔진은 내부 배열로 계산하고 틱이 끝날 때 q, qd, 자세만 공유메모리에 복사해 공개한다. 명령은 링 버퍼로 받아 틱 시작에 처리한다.
- Python을 **앱 안**에 두면 공유메모리 자체가 필요 없다 (함수 호출). 공유메모리는 Python을 분리해야 할 이유(안정성, 배포 분리)가 있을 때 값어치가 있다.

```
[엔진: 연속 배열로 계산] ──틱 끝에 복사──▶ [공유메모리(공개용)] ◀── Python 읽기
        ▲                                        │
        └── 틱 시작에 명령 소비 ◀── 명령 링 ◀─────┘ Python 쓰기
```

## 7. 통신(소켓) [결정: 지금은 열지 않음]

- Python이 같은 프로그램 안에 있거나 공유메모리로 붙는 동안은 네트워크 통신이 필요 없다.
- 명령이 들어오는 입구를 **하나로** 만든다 (명령 큐). Python도, 나중의 소켓 서버(`CSock`)도 같은 큐에 넣는다.
- 통신이 필요해지는 경우: 별도 프로그램이나 다른 PC/언어의 클라이언트, 실제 로봇/AMR 연동, 다중 클라이언트. 열 때는 기본 `127.0.0.1`, 외부 공개는 명시적으로.

## 8. 현재 엔진과의 관계 (확인 필요)

- 동역학(RNEA, 질량행렬, 중력 토크)과 역기구학은 C++로 구현되어 있다 (`Core/CDynamics`, `Core/CKinematics`).
- `Core`는 **정적 라이브러리**라 DLL이 없다. DLL로 쓰려면 `extern "C"` 평탄 함수로 감싸고 내보내기 매크로와 SHARED 타깃이 필요하다.
- 현재 시뮬레이션은 모터 토크를 받는 구조가 아니라 "관절 값 직접 지정"에 가깝다. 제어기가 토크를 내는 구조로 가려면 **엔진에 모터 토크 입력 경로가 먼저 필요**하다 [열림: 코드 확인 필요].
- 물류 공정(`CProcess`)은 이미 `main`에 있다: 지점 A/B, 물건 상태와 이벤트(출발/도착). 스크립트의 이벤트 소스로 쓸 수 있다.
